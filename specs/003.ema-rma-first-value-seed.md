# 003 — EMA and RMA seed their first value from one input too few

## §1. Definition

### §1.1 Expected

`EMA` and `RMA` are both exponentially smoothed averages seeded with a
simple average, which is the definition TA-Lib and TradingView compute
and the one both classes' own doc comments state ("Initial EMA = SMA of
first N periods", "First RMA = SMA(n) for initialization"):

- §1.1.1 The first emitted value is the simple average of the **first
  `interval` inputs** — all `interval` of them, including the one that
  completed the window.
- §1.1.2 Every later value is `prev + alpha * (input - prev)`, with
  `alpha = 2 / (interval + 1)` for `EMA` and `1 / interval` for `RMA`.
- §1.1.3 A corollary that needs no reference implementation to check:
  the average of a constant series is that constant, from the first
  emitted value on. `EMA(3)` over `10, 10, 10, …` is `10`.
- §1.1.4 `interval = 1` degenerates to the input itself (`alpha = 1`).
- §1.1.5 A `NaN` in the input must not be averaged into the seed, nor
  poison the average permanently.

### §1.2 Actual

- §1.2.1 The first emitted value is the sum of the first
  `interval - 1` inputs divided by `interval` — the average of one
  input too few — so it starts low by a factor of
  `(interval - 1) / interval` for a positive series.
- §1.2.2 Later values are correct in form (§1.1.2 holds) but inherit
  the wrong seed, so the error decays over roughly the average's own
  time constant rather than being absent.
- §1.2.3 `EMA(1)` and `RMA(1)` emit `NaN` forever: the window fills on
  the very first input, so the running total is never initialised and
  `NaN / 1` is `NaN`.
- §1.2.4 A `NaN` anywhere inside the first window makes the seed `NaN`,
  and because the seed slot is only ever written once the average is
  `NaN` for the rest of its life. A `NaN` after the first value leaves
  the average continuing from its stale previous value as if the gap
  had not happened.

## §2. Evidence

All of the following was observed against `src/` at `1d7d3f9`, on this
host, with the reporter's own network-free reproduction
(`repro-ema-rma-seed.cjs`) and a state probe.

- §2.1 Constant series, the §1.1.3 corollary:

  ```
  EMA(3)  6.667  8.333  9.167  9.583  9.792  9.896
  RMA(3)  6.667  7.778  8.519  9.012  9.342  9.561
  ```

  `6.667` is `10 * 2/3` = `10 * (n-1)/n`.

- §2.2 A 3 000-value seeded random walk against the §1.1.1/§1.1.2
  definition. First value relative error, and bars still more than
  1e-6 off:

  ```
  EMA(9)   11.069 %    53 bars      RMA(9)   11.069 %     99 bars
  EMA(20)   4.987 %   109 bars      RMA(20)   4.987 %    211 bars
  EMA(50)   1.987 %   248 bars      RMA(50)   1.987 %    492 bars
  EMA(200)  0.508 %   857 bars      RMA(200)  0.508 %   1723 bars
  ```

  Each first-value error is exactly `1/n`.

- §2.3 A subclass probe printing `_state[2]` around each `calculate()`
  on `EMA(3)` over constant `10`s. This is the direct observation that
  the branch does not run for the `n`-th input, rather than an
  inference from the output:

  ```
  input #1: in=10 isFilled=false sum:NaN->10  out=null
  input #2: in=10 isFilled=false sum:10 ->20  out=null
  input #3: in=10 isFilled=true  sum:20 ->20  out=6.666666666666667
  ```

  Input #3 is the one that fills the window, and the sum does not move
  for it: `20 / 3`, two inputs averaged over three.

- §2.4 The library's own `SMA` is the control. `SMA(3)` over the same
  constant series emits `10`, because its rolling sum is updated on
  every input *before* the `isFilled` test rather than only inside the
  not-yet-filled branch.

- §2.5 `ATR(14)` — an `RMA` of true range — over candles whose true
  range is always `100` emits `92.8571` as its first value
  (`100 * 13/14`), then `93.3673`, `93.8411`, …, confirming the defect
  reaches consumers unchanged and is not confined to direct `EMA`/`RMA`
  use.

## §3. Assumption

**Hypothesis, confirmed by §2.3 but recorded as the hypothesis the
tests must fail for.** `CircularArray.add()` sets `FILLED` as soon as
the write index wraps — that is, *during* the `n`-th `add()`, which
`LightIndicator.next()` performs before calling `calculate()`. So by
the time `calculate()` sees the `n`-th input, `h.isFilled` is already
`true` and the `if (!h.isFilled)` accumulate branch is skipped. The
running total therefore only ever sees inputs `1 … n-1`, and the next
branch divides it by `n`.

The state slot holding that running total (`SUM_FOR_INITIAL_EMA` /
`SUM_FOR_FIRST_RMA`, index 2) is therefore not merely mis-timed but
unnecessary: once the window is full it *is* the last `n` inputs, so
the seed can be read from the window itself.

## §4. Scope

- §4.1 `src/EMA/EMA.ts` and `src/RMA/RMA.ts` only. `SMA` (§2.4) and
  every other indicator in the library are correct; no other class
  accumulates into a state slot inside a `!isFilled` branch.
- §4.2 The exported state layout (a `Float64Array` of 3) must not
  change: states are exported and restored by consumers, and a restore
  of a state written by the current version must keep working.
- §4.3 Emitted values change for the first bars after a start. That is
  the point of the fix — those were the wrong ones — but it makes this
  a numeric-output change to a shared library (repo `CLAUDE.md`,
  "Coupling"), needing a version bump and a changelog note.
